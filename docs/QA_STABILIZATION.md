# Solace stabilization QA

6 November 2026 · Windows workspace · baseline commit `2b9bebc`

## Baseline and setup

- The working tree started clean on `main`. Read the two npm manifests and lockfiles, the Expo configuration, Android Gradle project, build scripts and test entry points. The runtime wrapper selected Node **24.22.1** over the Windows default Node 20. Doctor confirmed installed Expo **58.0.23**, React Native **0.88.1**, `expo-haptics`, `expo-image-picker`, server `tsx` and Sharp. No dependency reinstall or upgrade was needed.
- `npm run dev -- --web --localhost --port 8091` started the real Express API and Metro with a disposable SQL.js SQLite database in ignored `work/`. The first sandbox run failed with loopback `EACCES`. The same restriction affected Supertest. Loopback-enabled runs succeeded. Signup initially failed on port 8091 because the default CORS origins cover 8081, 8082 and 19006. Adding the two explicit 8091 loopback origins restored signup. This QA instance ran in offline-companion mode. The API and app read the same source as the normal development commands.
- The Android SDK and JDK 21 were available. ADB found a USB-connected Android 15 handset, model **2312FRAFDI**, 1080 × 2400 physical pixels at 440 dpi. The original stored text scale was 1.17, reported as 1.1 in the activity log. A Gradle init script under ignored `work/` assigned separate QA application IDs. The phone's existing Solace package and records were preserved. USB reverse connected only the QA ports. The first debug launch showed a blank surface while Metro was occupied. A dedicated Metro on port 8093 and a cold launch reached the welcome screen. The existing 8081 host process was left alone. Expo reported a cache deserialization error and recovered by crawling again. Web Expo emitted its expected unsupported push-token listener warning.
- Browser checks used IAB and Chromium 157 at 320 × 568, 320 × 640, 390 × 844, 430 × 850 and 430 × 932 CSS pixels, in Light and Dark. Browser media and selected network failures used synthetic fixtures. All accounts and text in captures are disposable QA data.

## Performance observations

- The chat offsets in defects 04 and 05 quantify interaction behavior. They are not animation frame-rate measurements.
- A single Chrome DevTools Protocol run at 320 × 568 Dark in the development export forced garbage collection after a warm-up and after 10 and 20 additional Chat → Voice Talk → Chat cycles. Used V8 heap was 7,045,712, 7,780,580 and 7,972,208 bytes respectively. This includes browser caches and bookkeeping and does not establish a native memory leak or release performance trend.
- The Android debug cold restart reported 1,798 ms of Activity launch time with a warm Metro cache. That metric does not include all JavaScript/font readiness. The initial native debug Metro bundle took 26,770 ms for 952 modules. The first-run number includes desktop bundling and USB transfer conditions, so it is not a packaged app startup baseline.
- `adb shell dumpsys gfxinfo` on the QA package after the Android chat and two-minute practice run reported 7,741 frames, 976 marked janky (12.61%), an 8 ms median and a 14 ms 95th percentile. The mixed debug sample includes development refresh and idle animation. It is not a release benchmark or a before/after comparison.
